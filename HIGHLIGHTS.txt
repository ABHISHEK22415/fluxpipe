FluxPipe — C++20 Video Processing Pipeline
==========================================

What it is
----------
A real-time multi-stage video processing pipeline built entirely from scratch
in modern C++20. No OpenCV. No FFmpeg. No external dependencies at all — just
the standard library and raw CPU intrinsics.

You feed it a video source (or let it generate one), it runs every frame
through a chain of filters concurrently, and spits out processed frames on the
other end. Think of it as a mini FFmpeg, but every part of it is written by
hand so you can see exactly how it works.


How it works (the interesting parts)
-------------------------------------
The pipeline is a chain of worker threads connected by bounded queues. While
thread 2 is blurring frame 5, thread 3 is already running edge detection on
frame 4. They all run in parallel. When the source runs out of frames, the
shutdown signal cascades automatically down the chain — no manual coordination.

The grayscale filter uses ARM NEON intrinsics (vld3_u8 + vshrn_n_u16) to
process 8 pixels in a single instruction. On x86 it switches to AVX2/SSE4
automatically at compile time. The fallback scalar path kicks in on anything
else. Zero runtime branching in the hot path.

The inter-stage queue is a wait-free SPSC circular buffer where the head and
tail counters sit on separate 64-byte cache lines. This eliminates false
sharing — producer and consumer cores never bounce the same cache line.

The Gaussian blur is two-pass separable, which is O(N*k) instead of O(N*k^2)
for a full 2D kernel. At radius 5 that's roughly a 5x reduction in operations.


Video generators (no input file needed)
----------------------------------------
- Plasma waves     — four sine wave interference fields, animated rainbow
- Mandelbrot zoom  — continuous deep zoom into the seahorse valley with
                     smooth orbit-trap colouring
- Fire simulation  — heat propagation convolution with a lava colour palette
- Reaction-diffusion — Gray-Scott model that grows Turing patterns (spots,
                       stripes, coral shapes) from a single seeded region


Filters
-------
- Grayscale with SIMD (NEON / AVX2 / SSE4 / scalar)
- Separable Gaussian blur (parallelised by row across a thread pool)
- Sobel edge detection
- Chromatic aberration (per-channel horizontal shift)
- Pixel sort glitch (sorts bright runs by luminance — aesthetic effect)
- Vignette (radial darkening)
- Color invert (NEON vmvnq_u8 — bitwise NOT on 16 bytes at once)


How this differs from just using OpenCV or FFmpeg
--------------------------------------------------
OpenCV and FFmpeg are production libraries. They are the right tool for most
jobs. FluxPipe is not trying to replace them. The difference is:

  - Every line is written by hand, so you can read it and understand it
  - The pipeline architecture, queues, thread pool, SIMD kernels — all visible
  - It compiles and runs with just cmake and clang/gcc, nothing else to install
  - The codebase is small enough (~1500 lines) to fit in your head

Using OpenCV gives you a result. Writing this gives you an understanding of
what OpenCV is actually doing internally.


Benchmark (Apple M-series, Release build)
------------------------------------------
  640x360  — glitch chain (3 stages)  :  ~1100 fps
  640x360  — full chain  (5 stages)   :  ~350  fps
  1280x720 — full chain  (5 stages)   :  ~37   fps

The bottleneck at 720p is the Gaussian blur (separable convolution is still
O(N*k) per pass). Replacing it with a box blur approximation or moving it to
the GPU would push well past 120fps at that resolution.


Use cases
---------
- Learning how concurrent pipelines work in practice
- Understanding SIMD without reading Intel/ARM manuals cold
- A base to add your own filters or generators
- Offline video effect processing (pipe output through ffmpeg to get an mp4)
- Benchmarking CPU SIMD throughput on different architectures


What I would build on top of this
-----------------------------------
- GPU compute stage via Metal (macOS) or CUDA for the blur
- A proper graph topology (fan-out, fan-in) instead of a linear chain
- Real video file input via a thin FFmpeg wrapper for the source stage
- A config file (JSON/TOML) to define the pipeline without recompiling


Build
-----
  mkdir build && cd build
  cmake .. -DCMAKE_BUILD_TYPE=Release
  make -j

  ./fluxpipe --demo fire --filter glitch --frames 120 --output out/
  ffmpeg -framerate 30 -i out/frame_%06d.ppm -c:v libx264 out.mp4
